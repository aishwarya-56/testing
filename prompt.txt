# Build Motor Insurance Surveyor Dispatcher

You are an experienced Python backend engineer. Build a **production-ready but intentionally simple and maintainable Motor Insurance Surveyor Dispatcher**.

The goal is to create a clean first version that can run locally without Kafka or Redis, while being structured so that Kafka and Redis can later be connected with minimal changes.

**Do not over-engineer this application.**

Prefer:

* Simple, readable Python
* Clear separation of business logic and infrastructure
* Small number of well-defined abstractions
* Strong automated tests
* Configuration-driven behavior
* Database-backed workflow state
* Straightforward error handling

Avoid introducing unnecessary frameworks, distributed workflow engines, complex event buses, excessive design patterns, or abstractions that do not provide real value.

# 2. Application Objective

Build a **Motor Insurance Surveyor Dispatcher**.

The application receives a motor accident/insurance claim request containing accident location information.

The dispatcher:

1. Receives the claim request.
2. Gets available surveyors.
3. Determines eligible surveyors.
4. Calculates their distance from the accident location.
5. Applies tier-specific rules.
6. Sorts candidates by distance.
7. Selects the configured number of surveyors.
8. Publishes a recommendation.
9. Waits asynchronously for surveyor responses.
10. If nobody accepts before the tier timeout, moves to the next tier.
11. If a surveyor accepts, assigns the claim.
12. Persists the important request, response, recommendation, and workflow state in the database.

The eventual production flow is:

```text
Insurance / Claims System
          |
          | Claim Event
          v
        Kafka
          |
          v
  Surveyor Dispatcher
          |
          +------> Redis
          |        Surveyor Data
          |
          +------> Database
          |        Request / State / Audit
          |
          +------> Kafka
                   Recommendation
```

Surveyor responses will also arrive through Kafka:

```text
Surveyor / Notification System
          |
          | ACCEPTED / REJECTED
          v
        Kafka
          |
          v
  Surveyor Dispatcher
```

The core dispatcher should be reusable from:

Conceptually:

```text
      |       |    |       |    |       |
    Memory  Redis Local   Kafka SQLite/Postgres
```

Use simple interfaces/protocols where they provide value.

Do not create abstractions for everything.

# 22. Candidate Selection

For every tier:

1. Find eligible surveyors.
2. Calculate their distance.
3. Apply the radius.
4. Filter by surveyor type.
5. Combine eligible candidates.
6. Sort the complete candidate list by distance ascending.
7. Select the configured number of candidates.

Do not select INTERNAL candidates first and then append EXTERNAL candidates.

# 25. Event-Driven Timeout — Critical Requirement

Do NOT implement:

```python
time.sleep(120)
```

to wait for surveyor acceptance.

Do not block a worker/request for the entire timeout.

Instead:

1. Create recommendation.
2. Persist current tier.
3. Persist a deadline.
4. Publish recommendation to Kafka.
5. Wait for acceptance/rejection events asynchronously.
6. Detect expired deadlines.
7. Generate a timeout event/transition.
8. Move to the next tier.

For example:

```text
Recommendation created
        |
        v
DB:
tier = 1
status = WAITING_FOR_RESPONSE
deadline = now + 120 seconds
        |
        v
Kafka recommendation
        |
        v
Wait for events
        |
        +---- ACCEPTED ---> ASSIGNED
        |
        +---- REJECTED ---> continue
        |
        +---- deadline ---> TIER 2
```

---

# 26. Restart-Safe Timeout

The timeout mechanism must survive application restarts.

Do NOT rely solely on:

```text
in-memory timer
```

because it disappears when the application crashes.

Instead, persist:

```text
deadline
```

in the database.

Use a lightweight background task that periodically finds:

```text
status = WAITING_FOR_RESPONSE
AND
deadline <= current_time
```

and processes those dispatches.

This is acceptable for the first production-ready version.

Do not introduce:

* Celery
* Kafka Streams
* Temporal
* Airflow
* Redis queues
* distributed workflow engines

unless there is a demonstrated requirement.

Keep the timeout worker simple.

---

# 27. Race Conditions

Consider:

```text
Tier 1 timeout
```

and:

```text
Tier 1 surveyor acceptance
```

happening at nearly the same time.

Also consider:

```text
Surveyor A accepts
Surveyor B accepts
```

nearly simultaneously.

Use database transactions/conditional updates so only one valid acceptance can win.

The database must be the final consistency boundary.

Do not rely only on Python locks.

* current tier
* deadline
* assignment
* recommendation history
* surveyor responses

* application restart
* timeout recovery
* duplicate Kafka messages
* concurrent processing

## Kafka Mode

I can start Kafka and send:

```text
claim.requests
```

The application consumes the claim.

It:

```text
Consume
 ↓
Validate
 ↓
Get surveyors
 ↓
Apply rules
 ↓
Persist
 ↓
Publish recommendation
```

to:

```text
surveyor.recommendations
```

Then a surveyor response sent to:

```text
surveyor.responses
```

causes the dispatcher to update the workflow.

A timeout causes the next tier recommendation to be published.

---

## Redis Mode

Changing:

```yaml
surveyor:
  provider: memory
```

to:

```yaml
surveyor:
  provider: redis
```

should switch the surveyor data source without changing dispatcher business logic.

The **database persists the workflow state**, Kafka transports business events, Redis provides production surveyor data, and FastAPI provides the local/demo interface.

Keep the core dispatcher independent of all three infrastructure technologies.
