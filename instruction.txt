# Motor Insurance Surveyor Dispatcher Engine — Discovery & Architecture Planning

I want to build a production-ready **Motor Insurance Surveyor Dispatcher Engine** in **Python using FastAPI**.

At this stage, **DO NOT implement the application or write production code yet**.

Your task is to thoroughly understand the requirements, inspect the available project files/context, identify ambiguities and missing decisions, and propose a detailed architecture and implementation plan.

## 1. Project Objective

The application will receive a motor accident/insurance claim request through a FastAPI API.

The request will contain accident location details, as shown in the provided `input_sample.json`.

The application must determine the most appropriate surveyor to dispatch by considering:

* Surveyor availability
* Surveyor location
* Geographic distance from the accident location
* Surveyor type
* Surveyor working/shift timing
* Tier-specific geographic search radius
* Tier-specific notification and acceptance timeout
* Surveyor acceptance/rejection/timeout
* Distance-based candidate prioritization
* Configurable number of surveyors to notify for each tier

The dispatcher should progress through multiple tiers until a surveyor accepts the request or no eligible surveyor remains.

## 2. Business Rules

The dispatcher has three tiers.

### Tier 1

* Configurable search radius
* Default radius: **10 km**
* Notify only **INTERNAL** surveyors
* Configurable acceptance timeout
* Default timeout: **120 seconds**

### Tier 2

* Configurable search radius
* Default radius: **15 km**
* Notify only **INTERNAL** surveyors
* Configurable acceptance timeout
* Default timeout: **60 seconds**

### Tier 3

* Configurable search radius
* Default radius: **15 km**
* Notify both:

  * INTERNAL surveyors
  * EXTERNAL surveyors
* Configurable acceptance timeout
* Default timeout: **60 seconds**

For each tier:

1. Find eligible surveyors within the configured search radius.
2. Filter surveyors based on availability.
3. Filter surveyors based on their shift/working time.
4. Filter surveyors based on surveyor type applicable to the tier.
5. Sort the combined INTERNAL + EXTERNAL candidate set by distance from the accident location.
6. Select the configured number of candidates.
7. Notify the selected candidates.
8. Wait for the configured acceptance timeout.
9. If a candidate accepts, stop the dispatch process and return the accepted surveyor.
10. If nobody accepts before the timeout, move to the next tier.
11. If there are no eligible candidates in the current tier, immediately move to the next tier.
12. If there are no candidates remaining in any tier, return an appropriate "no surveyor available" result.

The **combined candidate set must be sorted by distance before selecting the N candidates**.

A candidate is considered eligible when:

```text
availability == Available
AND
the surveyor is currently within their working shift
AND
the surveyor type is allowed for the current tier
AND
the surveyor is within the configured tier search radius
```

The dispatcher should maintain the configured buffer/logic around surveyor shifts so that a surveyor whose shift is about to expire can be handled appropriately. Please identify any ambiguity in this requirement and ask for clarification if necessary.

## 3. Distance Calculation

Initially, use the **Haversine distance** between:

* Accident location
* Surveyor location

for filtering and sorting candidates.

However, the design must be modular enough that the distance calculation/recommendation mechanism can later be replaced with **route distance**, such as distance obtained from a mapping/routing service.

Do not tightly couple the dispatcher business logic to the Haversine implementation.

Please propose an appropriate abstraction/interface for this.

## 4. Surveyor Data Source

In production, surveyor details will come from **Redis**.

However, Redis is **not available for the initial implementation**.

There is a reference project/component called:

`redis_surveyor_simulator.py`

Use this simulator to provide the surveyor data for now.

The simulator should behave as a temporary data provider that can later be replaced by a real Redis implementation without requiring major changes to the dispatcher business logic.

Please design an appropriate repository/provider abstraction.

For example, the architecture should conceptually allow:

```text
Dispatcher
    ↓
Surveyor Repository / Provider Interface
    ↓
Simulator implementation

Later:

Dispatcher
    ↓
Surveyor Repository / Provider Interface
    ↓
Redis implementation
```

The Redis connection should be created/reused appropriately and **must not create a new Redis connection for every incoming API request**.

The connection/data-access design should be production-ready and allow the Redis implementation to be introduced later with minimal changes.

* Notification/acceptance handling
* Timeout handling

Recommend an appropriate design for these concerns.

## 6. Notifications and Acceptance

The dispatcher should notify selected surveyors and wait for their acceptance/rejection.

For this initial implementation, the notification mechanism can be simulated/mocked.

However, the architecture should make the notification mechanism replaceable in the future.

Please propose abstractions for:

* Sending a notification
* Receiving/recording acceptance
* Receiving/recording rejection
* Handling acceptance timeout

The dispatcher should stop as soon as an eligible surveyor accepts.

Please consider what happens if multiple surveyors accept at nearly the same time and recommend how to ensure that only one surveyor wins the dispatch.
